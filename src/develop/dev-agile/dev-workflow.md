# 典型的中小团队开发流程详解 

> 不同公司的规模、文化与开发方式差异很大，研发流程也因此各不相同。本文梳理一个适合中小团队、相对完善的敏捷研发流程，并说明各阶段、各角色的产出与协作要点。

## 背景

在需求频繁变化、人手有限的团队里，「流程」既要保证质量，又不能过重。流程太轻，需求、开发、测试各自为战，容易返工；流程太重，则拖慢交付。中小团队通常采用前后端分离 + CI/CD + Scrum 的组合，把流程控制在「够用」的程度，并借助完善的代码分支、权限控制把协作风险降到最低。

需要说明的是，流程不是越标准越好，而是要匹配团队当前的问题。下面给出的是一个参考骨架，团队应结合自身规模、业务节奏与人员结构做裁剪。

## 一个典型的研发流程

下面按时间顺序拆解一次完整的迭代，每个阶段都对应明确的输入、活动与产出。

### 1. 需求阶段

- 产品经理（Product Owner）梳理需求，输出用户故事（User Story）与验收标准。
- 与开发、测试一起做需求澄清，明确边界与优先级，避免「一句话需求」。
- 产出：需求列表、用户故事、验收标准。

需求阶段的目标不是把需求写到多细，而是让「做什么」与「不做什么」达成一致。一个模糊的需求如果被直接带进开发，返工成本会成倍增加。

### 2. 设计与评审

- 开发负责人做技术方案设计（接口、数据模型、关键流程），必要时给出原型。
- 组织设计评审，前后端、测试共同参与，尽早暴露接口与依赖问题。
- 产出：技术方案、接口文档（如 OpenAPI / Swagger）。

设计评审的目的不是走流程，而是让不同角色在编码前就对接口、边界与风险形成共识，避免「开发完才发现方案不成立」。

### 3. 开发与联调

- 采用前后端分离：前端基于框架开发页面，后端提供数据接口（RESTful API）。
- 每个 Sprint 通常为 2–4 周，长度按用户故事体量调整。
- 开发完成后进行前后端联调，配合单元测试保证基本正确性。
- 产出：可运行的代码、单元测试、联调通过的功能。

开发阶段要避免「大分支、晚集成」：小步提交、频繁合入，能让集成风险始终处于可控范围。

### 4. 测试

- 测试人员根据验收标准执行功能测试、回归测试，关键路径做接口自动化。
- 缺陷提交到缺陷管理系统，按优先级修复并回归。
- 产出：测试报告、缺陷清单。

测试阶段的价值不仅是「发现问题」，更在于用验收标准判断功能是否真正交付。让测试人员在需求与设计阶段就参与（测试左移），能显著降低缺陷修复成本。

### 5. 发布与回归

- 通过持续集成 / 持续交付（CI/CD）流水线构建与部署。
- 灰度或分批发布，线上回归后验收。
- 产出：发布记录、上线报告。

发布不是终点：上线后要观察关键指标与告警，确认无异常后再进入下一轮迭代，形成「需求—开发—发布—反馈」的闭环。

## 敏捷仪式与团队协作

Scrum 提供了一组固定的会议节奏，把协作固化为习惯：

- **Sprint 计划会**：从需求池挑选本迭代要完成的用户故事，明确迭代目标并拆分任务。
- **每日站会**：每人用「昨天做了什么、今天做什么、有无阻碍」三句话同步进度，控制在 15 分钟内，重点是暴露阻碍而非汇报。
- **Sprint 评审会**：向产品与相关方演示可运行的成果，收集反馈。
- **Sprint 回顾会**：复盘本迭代的过程问题，形成可执行的改进项。

除会议外，还需明确协作契约：需求进入开发前必须澄清验收标准；接口变更要同步前后端；缺陷按优先级流转，避免「插队」打乱节奏。

## 角色与产出对照

| 阶段 | 主要角色 | 关键产出 |
| --- | --- | --- |
| 需求 | 产品经理 | 用户故事、验收标准 |
| 设计 | 开发 / 架构 | 技术方案、接口文档 |
| 开发 | 开发 | 代码、单元测试 |
| 测试 | 测试 | 测试报告、缺陷清单 |
| 发布 | 运维 / 开发 | 发布记录、上线报告 |

## 分支与协作规范

- 采用清晰的分支模型（如主干 + 特性分支），**集成分支禁止直接推送，统一走合并请求（Pull Request）评审**。
- 提交信息规范化，代码合并前必须通过评审与流水线检查。
- 权限按角色分配，重要分支设置保护规则。

分支策略要与发布节奏匹配：主干保持随时可发布，功能在短生命周期的特性分支上开发，通过 PR 合入。分支生命周期过长会累积合并冲突，是很多团队踩过的坑。

## 持续集成与持续交付

- 每次提交触发构建与自动化测试，尽早发现问题。
- 环境隔离：开发、测试、预发、生产环境相互独立。
- 制品（构建产物）集中管理，镜像禁止使用 `latest` 这类可变标签，保证可追溯。

流水线应至少覆盖：编译、单元测试、静态检查与制品打包；测试环境可自动部署，生产环境人工触发。这样既保证每次提交都被验证，又保留上线的可控性。

## 常见问题与改进方向

- **需求变更频繁**：用较短的 Sprint 与持续的需求澄清缓冲变化。
- **联调成本高**：尽早冻结接口、提供 Mock 服务。
- **测试成为瓶颈**：提升接口自动化比例，把质量内建于开发阶段（参考 [TDD](./dev-pratice-tdd.md)）。
- **流程形同虚设**：明确各阶段就绪 / 完成定义，避免「跳步」。

流程落地还有一个常被忽略的要点：**每个阶段都要有可验证的产出**。需求要有验收标准，设计要有接口文档，开发要有可运行代码与测试，测试要有报告。产出就是「就绪」与「完成」的判断依据，没有产出，流程就会退化成形式。

## 研发流程的裁剪原则

流程不是越完整越好，裁剪时要遵循几条原则：

- **按团队规模**：三五人的小团队可以省去正式评审会，用代码评审与站会替代；团队变大后再逐步引入更重的机制。
- **按业务节奏**：需求变化快、上线频繁的业务，宜缩短迭代、提高自动化程度；需求稳定的项目可以适当拉长周期。
- **按风险等级**：涉及资金、安全的功能，测试与评审要更严格；内部工具则可以轻量处理。
- **持续演进**：流程本身也要复盘，定期审视哪些环节已无价值、哪些环节长期是瓶颈。

裁剪的目标是让流程服务于交付，而不是让交付迁就流程。

## 小结

- 中小团队的流程应以「够用」为度：需求 → 设计 → 开发 → 测试 → 发布，闭环清晰。
- 需求、设计、开发、测试、发布五个阶段，每一环都要有明确的就绪与完成标准。
- 站会、评审、回顾等敏捷仪式，是把协作固化为习惯的载体。
- 前后端分离与 CI/CD 是提效的两大支柱。
- 每个阶段都要有明确的角色与产出，避免口头传递造成返工。
- 集成分支走 PR 评审、镜像不带可变标签，是质量与可追溯的底线。
- 流程要随团队与业务演进，定期复盘、按需裁剪，避免为了流程而流程。
